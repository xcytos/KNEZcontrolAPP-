# MCP Forensic Audit & Correction Plan

## Phase 1: MCP Spec & Reality Alignment
**Problem**: The system reports "READY" prematurely and uses UI-driven state rather than protocol-driven truth.
**Evidence**: `TaqwinMcpService.ts` explicitly sets "READY" after `listTools` succeeds, but the UI consumes this state optimistically even if the underlying connection is unstable or tools return empty. The logs show "initialize ok" (handshake success) but subsequent `tools/list` timeouts, yet the UI remains "Operational".
**Root Cause**:
1.  **Simulated State**: `READY` is a string literal in the service, not a derived state from the active connection's health check.
2.  **Frontend Fetch**: DuckDuckGo/Jina searches use `fetch()` in `ExtractionService.ts` (browser context), violating the MCP model where tools should execute server-side or via a controlled proxy.
3.  **UI Layout**: `McpRegistryView` has fixed-width modals and non-breaking text causing overflow.

**Fix Strategy**:
1.  **Strict State Machine**: Redefine `READY` to mean `(isConnected && hasCapabilities && initialPingSuccess)`.
2.  **Server-Side Tools**: Move DuckDuckGo/Jina logic to a Python/Node MCP tool or a backend proxy, removing direct browser fetches.
3.  **UI Truth**: Bind UI "Health" indicators to real-time `ping` or `listTools` results, not just the initial "process started" event.
